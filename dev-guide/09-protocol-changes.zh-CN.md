# 修改通信协议

*[English](09-protocol-changes.md)*

"协议"指的是设备↔后端之间的 HTTP 通信格式，记录在
《[protocol/hardware-communication-protocol.md](../protocol/hardware-communication-protocol.zh-CN.md)》
的 §1-9——请求/响应的 JSON 格式、错误码、串口配网指令，以及 §9 的指令通道。改协议跟本手册里其他
每一章都不一样：这是唯一一个固件仓库和后端仓库必须真正互相对齐、而不是各自独立构建测试通过就行
的地方。

## 故意没有版本号这回事

自己去查一下这几处的线格式就知道（`server/internal/protocol/protocol.go`，或者协议文档里到处
都有的 JSON 示例）——没有版本号，没有能力协商，什么都没有。§0 里写明的理由是：把所有对"用尽量少
的配置让数据跑起来"这个目标不是严格必要的东西都去掉，而版本协商这种机制正好就是这条路径上完全
不需要的那种东西。这个后果完全落在改协议的人身上：**默认后端和每一台设备的固件在任何时刻都对
这个通信格式达成一致**，协议本身没有任何机制去检测或处理两边不一致的情况。

## "只加不改"还是"破坏性改动"——这个区分就是这一章的全部内容

**只加不改**（可以按任意顺序上线——先上后端或者先上固件都行，因为老的一方遇到自己不认识的东西
就直接忽略）：

- 给某个已有请求/响应加一个新的可选字段，照着 §9 `cmd` 字段的样子来：*只在相关时才出现,不相关
  时整个省略（不是发一个 `null`）*——一台从没听过 `cmd` 的设备根本不会去找这个 key，cJSON 解析
  一个多带了个它没索取的字段的对象也什么都不会发生。
- 给 §9 的指令通道加一个新的 `action`（见[第 7 章](07-firmware-add-server-command.zh-CN.md)）——
  老固件会走进它 `if`/`else if` 链的 `else` 分支，打一行"unrecognized cmd.action"的日志，没有
  更坏的后果。
- 加一个新的错误码 `c`（§8）——不特别处理它的固件本来就应该有一个通用的兜底分支（下个周期重试），
  而不是一个遇到没见过的值就崩掉的穷举 switch；如果没有，那本身就是一个值得修的固件 bug，跟这次
  改动无关。
- 加一个新的串口配网指令（§1.2，见[第 6 章](06-firmware-add-serial-command.zh-CN.md)）——现有
  指令什么都不变。

**破坏性改动**（要求后端和**每一台设备的固件**一起更新——不存在什么安全的先后顺序，也没法在
升级过程中让新老设备混着跑）：

- 重命名或删除某个现有固件依赖的字段。
- 改变某个已有字段的类型或含义（比如某类设备的 `field3` 不再表示"光照"了）。
- 改变某个错误码的含义，或者去掉协议目前强制要求的某个设备行为（比如 §8/§4 里的
  ±5 分钟时间戳窗口）。

如果拿不准一个改动属于哪一类，问自己一句："一份没改过的 `ubibot-open-ws1b` 当前固件，去连新的
后端，还能跟原来一样正常工作吗？"如果答案是"能"，那就是只加不改。如果答案是"不能，或者我不确定"，
就当破坏性改动来对待，提前规划好上线顺序——对这个项目来说，几乎总是意味着：先更新固件、推到设备
上，*然后*才上后端的改动，因为"设备迟迟没升级到新固件"比"后端迟迟没部署"要常见得多。

## 附录是一份真实的变更记录，不是摆设

协议文档自己的**附录：本版本中移除的能力**存在的原因是，这个协议曾经比现在大得多（设备密钥签名、
会话 token、配置轮询、OTA、一套激活/密钥绑定流程），后来被刻意精简成了现在这个最小化的样子
（§0）。注意它自己的提示："**§9 后来重新引入了一个刻意做得很窄的 `cmd` 字段**……原来那个通道
剩下的部分依然不在范围内。"如果你以后要移除某个能力，也要用同样的诚实态度把它加进这份列表——如果
你以后想把这份列表里的某个东西加回来，要把它当成一个值得正儿八经拿出来讨论的设计决策（见
《[手册说明](00-overview.zh-CN.md)》里关于范围的那条说明），不是当成一个普通的新功能来加。

## 具体要改哪些地方

1. `protocol/hardware-communication-protocol.md` 里对应的 `§N` 小节——请求/响应格式、字段表、
   设备行为。
2. 如果你移除了什么，更新附录。
3. 文档里为受影响小节引用的两份参考实现链接（比如 §1.2 指向 `ubibot-open-ws1b` 的
   `provisioning.c`，§9 指向 `command.c`）——这些不是强制要求完全对得上（文档写的是"鼓励……但不
   强制"），但它们是这个项目自己的测试真正跑过的实现，所以要保持它们说的是实话。
4. 如果这个改动同时也影响了某个后台触发的接口（就像 §9 的指令那样），更新
   [api/admin-api.md](../api/admin-api.zh-CN.md)。
