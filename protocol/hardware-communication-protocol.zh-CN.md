# UbiBot 开放平台硬件通信协议

*[English](hardware-communication-protocol.md)*

### 0. 项目范围与本版本修订说明

本项目（ubibot-open）是一个面向内部/教学使用的开源物联网平台——不追求完整性、可靠性或生产级
安全性。首要目标是：让用户用尽量少的步骤、尽量少的配置，把硬件接上去、看到数据。任何不是"让数据
跑起来"这条核心路径严格必需的复杂认证流程、状态机，或者指令下发通道，都被剥离掉了。

跟早期版本相比，这个修订版：

- 面向的是一个可信的内部网络环境，所以设备身份认证也被简化掉了：不再有 DeviceSecret 或者签名
  计算——设备用明文的 pid+sn 标识自己，不需要在平台上预先创建设备，也不需要走"自助激活审批/
  密钥绑定"流程。上电、联网，就能上报数据。
- 去掉了单独的"激活"步骤（设备激活/token 会话）：一次数据上传请求直接用 pid+sn 标识自己，一次
  请求就完成写入。保留了一个轻量级的、不需要认证的时间同步接口，让没有本地时钟的设备能拿到当前
  时间。
- 去掉了原来那个大得多的指令下发通道：配置轮询、自定义探头配置、OTA，这些都仍然不在范围内——
  对"让数据跑起来"这个核心目标不是必需的，教学/演示场景里也很少用到。后来又刻意加回了一个很窄的
  例外（§9）：管理员可以排一个 `reboot` 或 `set_interval` 指令，随设备自己下一次上报捎带送达，
  没有应答——不是一个通用的推送通道，只够避免为这两件事跑一趟现场重新刷机。
- 上报的数据不再用 `temperature`/`humidity` 这种具名字段——统一成了 `field1`–`field20`（最多
  20 个），平台原样存储，不关心它们的业务含义。`field1`/`field2`/`field3` 带一个约定俗成的默认
  含义（温度/湿度/光照）；其余的完全由用户自己定义。

本文档剩下的部分，描述的就是这个新的、简化过的协议。

### 1. 设备配网（首次联网配置）

一台刚出厂或者刚恢复出厂设置的设备，本地没有任何 WiFi 配置，需要先配网——连上 WiFi、指向正确的
服务器地址——才能用下面章节描述的 HTTP 协议上报数据。

#### 1.1 蓝牙配网

**目前不支持。** 没有提供基于蓝牙（BLE）的配网方式；现场的 WiFi 和服务器配置完全通过下面的
串口配网（§1.2）来做。

#### 1.2 串口配网

设备通过它的 USB/UART 串口接受一组文本指令。配合 `ubibot-serial-sync`（或者任何跟固件日志输出
波特率一致的串口终端——ESP-IDF 参考固件默认是 115200），可以在现场不重新编译、不重新烧录的情况
下设置 WiFi、服务器地址，以及设备自己的序列号——尤其是，这让"一份编译好的固件镜像（一个 pid，
不预置 sn）"可以烧录进整批产线设备，之后再通过串口给每台物理设备设置它自己的 sn。指令是单行、
UTF-8 编码的 JSON，通过串口发送。

**设置网络**

```json
{"command":"SetupWifi","ssid":"","password":"","type":""}
```

| 字段 | 类型 | 是否必填 | 说明 |
| --- | --- | --- | --- |
| command | string | 是 | 固定值 `SetupWifi` |
| ssid | string | 是 | WiFi 网络名 |
| password | string | 否 | WiFi 密码；开放网络可以省略或留空 |
| type | string | 是 | WiFi 认证/加密类型（具体接受哪些值由固件实现决定，比如 `WPA2`/`OPEN`） |

**设置服务器地址**

```json
{"command":"SetupServer","host":"127.0.0.1","port":8080}
```

| 字段 | 类型 | 是否必填 | 说明 |
| --- | --- | --- | --- |
| command | string | 是 | 固定值 `SetupServer` |
| host | string | 是 | 服务器的 IP 地址或域名——后端 §2（传输）章节所说的通信对象 |
| port | number | 是 | 服务器监听端口 |

**设置设备的序列号**

```json
{"command":"SetupDevice","sn":"RV41554WS1B"}
```

| 字段 | 类型 | 是否必填 | 说明 |
| --- | --- | --- | --- |
| command | string | 是 | 固定值 `SetupDevice` |
| sn | string | 是 | 设备自己的序列号（§3） |

没有办法通过这种方式设置 `pid`——同一份固件镜像烧出来的每一台设备，都应该共用同一个 `pid`；
只有 `sn` 才需要每台设备各不相同。

**应答（ACK）**：处理完每条指令之后，设备会通过同一个串口写回一行 JSON：

```json
{ "c": 0, "msg": "wifi saved" }
```

| 字段 | 说明 |
| --- | --- |
| c | 0 = 成功；1 = 校验失败（字段缺失、类型不对、太长等等）；2 = 校验通过但持久化保存失败（比如存储写入出错） |
| msg | 一句简短的说明——成功和失败的原因都可能出现在这里；不是给机器解析用的枚举值 |

**什么时候生效**：一旦保存成功，新值会**立刻在本次运行中生效**——不需要额外重启；下一次尝试
联网/上报数据用的就已经是新值了。它也会被写入非易失存储（比如 NVS），所以能扛住断电和深度睡眠
唤醒，直到再次被覆盖为止。

**配网窗口**：设备不需要一直监听串口指令。参考实现只在**上电时**打开一个限时窗口（收到最后一个
字节之后，静默一段时间就会提前关闭；不管有没有活动，都有一个硬性总时长上限）；窗口关闭之后，
设备就转入正常的联网/休眠周期。定时器唤醒（相对于上电而言）不会重新打开这个窗口，所以常规的
上报周期不会被卡住等待。具体的时长、以及是否要在上电之外的场景打开这个窗口，留给固件实现自己
决定——这份协议不做强制要求。

上面的应答格式和生效时机行为，反映的是 `ubibot-open-ws1b` 参考固件的实现（见该仓库的
[main/provisioning.c](https://github.com/ubibot-open/ubibot-ws1b/blob/main/main/provisioning.c)）。
其他固件实现也鼓励遵循同样的约定以保持一致性，但这不是强制要求。

### 2. 传输

| 项目 | 要求 |
| --- | --- |
| 协议 | HTTP |
| 方法 | POST |
| 数据格式 | JSON，UTF-8 |
| Content-Type | application/json |

注意：这个协议完全没有做任何身份认证——它完全信任请求里的 pid+sn。只适合用在可信的内部网络
环境里；不要把这套方案直接用在需要真正安全性、或者暴露在公网上的部署场景中。

### 3. 设备身份

设备用两个字段标识自己，都是明文发送，不需要密钥/签名：

| 字段 | 说明 |
| --- | --- |
| pid（ProductID） | 产品型号，用来区分设备类型 |
| sn（SerialNumber） | 设备的唯一序列号 |

### 4. 时间同步

当设备没有本地时钟时（首次上电，或者断电导致 RTC 复位），可以调用这个接口获取服务器当前时间。
这个接口完全不做身份校验——不需要签名，也不验证签名。

**POST /api/v1/auth/time**

请求：

```json
{ "pid": "ubibot_open_dev_v1", "sn": "sn_ws1_20001_1"}
```

响应：

```json
{ "c": 0, "t": 1788950400 }
```

| 字段 | 说明 |
| --- | --- |
| t | 服务器当前的 Unix 时间戳，单位秒 |

### 5. 数据上报（唯一面向设备的数据接口）

**POST /api/v1/data/report**

请求体：一次上报可以携带多条带时间戳的读数（比如设备离线期间缓存的好几轮数据）：

```json
{
  "pid": "ubibot_open_dev_v1",
  "sn": "sn_ws1_20001_1",
  "ts": 1788950400,
  "payloads": [
    { "ts": 1788950400, "field1": 25.6, "field2": 60.2 },
    { "ts": 1788951000, "field1": 25.8, "field2": 59.9, "field3": 812 }
  ]
}
```

| 字段 | 类型 | 是否必填 | 说明 |
| --- | --- | --- | --- |
| pid | string | 是 | 产品型号 |
| sn | string | 是 | 设备序列号——识别设备的唯一依据（不做签名校验） |
| ts | Int64 | 是 | 发起这次请求时的 Unix 时间戳（秒），用于一个基础的时间窗口校验（可选校验，见 §8） |
| payloads | array | 是 | 一条或多条记录。通常一条记录对应一个采样点、携带那个时刻的所有字段；也可以把一轮采样拆成多条记录，每条只带一个或几个字段（见下面的"按时间窗口合并"）——服务器对这两种写法处理效果是等价的 |
| payloads[].ts | Int64 | 是 | 这个采样点的 Unix 时间戳（秒）（可以早于外层的 `ts`，用于补发离线期间缓存的数据） |
| payloads[].field1~field20 | number | 是 | `field1`–`field20` → 数值，见 §6。没用到的字段编号整个省略——不要发一个空值 |

**按时间窗口合并**：不要求"一条记录 = 一个完整的采样点"——同一轮采样的各个字段可以拆分到多条
记录里（比如传感器是依次读取的，每个字段的 `ts` 相差几秒）。服务器按 `ts` 对 `payloads` 分组：
排序之后，从第一条还没分组的记录开始新建一组，后续任何 `ts` 落在这一组锚点（组内第一条记录的
`ts`）60 秒以内的记录，都加入同一组；超过锚点 60 秒的，就开始新的一组，当作独立的一轮采样。
同一组内的记录会被合并保存成一个数据点（`ts` 取这一组的锚点；如果同一个字段编号在组内出现多次，
以最后一次出现的为准）。**超过 60 秒的永远不会被合并**，哪怕只是比上一组的窗口晚了几秒——每一轮
都是独立的数据点，出现在同一个请求里不代表可以被盲目地合并成一条。

举个例子，看这个请求（真实硬件里常见的写法——一条记录一个字段——其中两轮采样时间相隔较远）：

```json
{
  "pid": "ubibot-ws1b",
  "sn": "RV41554WS1B",
  "ts": 1514767409,
  "payloads": [
    { "ts": 1514767395, "field1": 29.291221618652344 },
    { "ts": 1514767395, "field2": 40.831615447998047 },
    { "ts": 1514767395, "field3": 439.95001220703125 },
    { "ts": 1514767395, "field4": 0.014166667126119137 },
    { "ts": 1514767395, "field6": 26.9375 },
    { "ts": 1514767395, "field7": 27.625 },
    { "ts": 1514767409, "field5": -56 }
  ]
}
```

这 7 条记录里最大的 `ts` 差是 1514767409 − 1514767395 = 14 秒，在 60 秒窗口以内，所以全部合并
保存成**1 个数据点**（`ts=1514767395`，包含 7 个字段：field1–field4、field6、field7、field5）。

再对比一下两轮采样时间隔得更远的情况（第二轮比第一轮晚 2 分钟）：

```json
{
  "pid": "ubibot-ws1b",
  "sn": "RV41554WS1B",
  "ts": 1514767515,
  "payloads": [
    { "ts": 1514767395, "field1": 29.29, "field2": 40.83 },
    { "ts": 1514767515, "field1": 29.31, "field2": 40.79 }
  ]
}
```

这两个 `ts` 相差 120 秒，超过了 60 秒的合并窗口，所以会保存成**2 个独立的数据点**
（`ts=1514767395` 和 `ts=1514767515` 各自独立），而不是合并成一个。

响应：

```json
{ "c": 0, "t": 1788950400 }
```

| 字段 | 说明 |
| --- | --- |
| c | 业务状态码——0 表示成功，其他取值见 §8 |
| t | 服务器当前的 Unix 时间戳（秒）；设备可以用它来校准本地时钟（可选，不强制） |

服务器行为：
- 如果 `sn` 是从没见过的，会自动创建一条设备记录（pid/sn/首次出现时间等等）；之后就按已有设备
  处理。
- 如果设备已经被管理员手动停用，这个接口会拒绝这台设备的所有数据（见 §8——停用是针对一台已有
  设备的管理员操作，不是新设备接入的前置条件）。

### 6. 数据字段（field1 – field20）

不再使用 `temperature`/`humidity` 这类具名传感器字段——全部统一成了编号字段，最多 20 个。平台
原样存储每个编号下的数值，不关心每个编号代表什么物理量，除了下面这 3 个字段带有一个约定俗成的
默认含义：

| 字段 | 默认含义 |
| --- | --- |
| field1 | 温度 |
| field2 | 湿度 |
| field3 | 光照强度 |
| field4 – field20 | 完全由用户自己定义（比如 CO2、土壤 pH 值、电池电压等等）——平台不做任何假设 |

这个默认含义只是一个用于管理控制台展示（比如图标、单位）的约定——在协议层面并不强制。设备完全
可以只上报 `field1`，或者从 `field4` 开始上报；不管哪种情况，平台都会照单全收。

### 7. 设备管理（管理控制台一侧，不属于面向设备的协议）

下面这部分不是设备需要实现的东西——它描述的是管理控制台的行为，帮助理解 §5 提到的"自动创建/
停用"行为：

- 设备第一次成功上报数据时，会自动出现在管理控制台的设备列表里——不需要提前创建。
- 管理员也可以**可选地**提前批量预注册一批设备（比如从一批产线设备的序列号清单），通过批量导入
  ——纯粹是命名/打标签上的便利，不是前置条件：没导入过的设备照样会在第一次上报时自己出现，跟
  上面说的一样。预注册的设备是靠 `sn` 跟真实设备的第一次上报匹配的，跟其他情况一样。
- 管理员可以在控制台里给设备改名、查看历史数据、启用/停用，或者连同它的所有数据一起删除，也
  可以把设备归到某个**产品**下（设备型号的名称/描述，按 `pid` 匹配解析——纯粹是展示元数据，
  不是设备能上报数据的前置条件）。
- 设备一旦被停用，它之后所有的上报请求都会被拒绝（数据不再被处理）；重新启用会恢复正常行为。
- 删除一台设备会连同它的所有历史数据一起永久删除。删除一个产品只会移除它的展示元数据——已经
  匹配到它 `pid` 的设备不受影响。

### 8. 错误处理

| HTTP 状态码 | c | 场景 | 设备行为 |
| --- | --- | --- | --- |
| 200 | 0 | 成功 | 正常处理 |
| 400 | 1002 | 时间戳超出 ±5 分钟窗口 | 检查本地时钟，或者调用 §4 的时间同步接口校准后重试 |
| 400 | 1003 | 请求体格式不对 | 检查固件的序列化逻辑；下个周期重试 |
| 401 | 1103 | 设备已被管理员停用 | 停止重试并报警（LED/日志）；需要人工介入 |
| 429 | 1900 | 被限速 | 丢弃这次上报；等下个周期 |
| 5xx | 5000 | 服务端故障 | 下次上报周期重试 |

### 9. 指令下发（管理员触发，可选）

这是 §0/§2"服务器到设备没有通道"这一立场的唯一例外，而且刻意做得很窄：管理员可以从管理控制台
给每台设备排**最多一个**指令，会随这台设备**下一次 `POST /api/v1/data/report` 的响应**捎带
送达——没有新接口，没有设备主动轮询，没有推送。一台从来不去看这个字段的设备完全不受影响；
§2–§8 的一切都不变。

**带有排队指令的响应**（§5 的正常响应，多了一个 `cmd` 字段）：

```json
{ "c": 0, "t": 1788950400, "cmd": { "action": "reboot" } }
```

```json
{ "c": 0, "t": 1788950400, "cmd": { "action": "set_interval", "seconds": 600 } }
```

| 字段 | 说明 |
| --- | --- |
| cmd | 只有这台设备有排队中的指令时才会出现——没有指令的时候会整个省略（不是 `null`） |
| cmd.action | `reboot` 或 `set_interval`——见下表 |
| cmd.seconds | 只有 `set_interval` 时才有：新的上报间隔，单位秒 |

| action | 设备行为 |
| --- | --- |
| `reboot` | 立刻重启 |
| `set_interval` | 持久化新的间隔（比如存到 NVS），从**下一个**休眠/上报周期开始应用——正在进行中的这一轮，还是按开始时生效的那个间隔跑完 |

**送达语义——用它之前一定要读**：
- **每台设备最多排一个指令。** 排一个新的会覆盖还没送达的那个；不存在多个指令排队等候。
- **送达一次之后就清空——发了不管。** 指令一旦被嵌入某次上报的响应，平台就认为它已经送达并
  清空了，不管设备到底有没有真的收到或者执行（响应包丢失、设备刚收到就崩溃……在平台看来都跟
  "已送达"一样）。没有任何形式的应答、重试或者送达确认。
- **指令排队等待的时长没有上限。** 具体什么时候送达，取决于这台设备下一次上报是什么时候——如果
  它每隔几分钟就上报一次，几乎是立刻；如果它上报很少或者处于离线状态，可能要等很久。
- `seconds` 的取值范围（`set_interval` 接受多小/多大的值）是一个**admin API 层面**的问题，不是
  这个线格式本身的一部分——设备应该信任这个字段携带的任何值。

上面的应答格式和生效时机行为，反映的是 `ubibot-open-ws1b` 参考固件的实现（见该仓库的
[main/command.c](https://github.com/ubibot-open/ubibot-ws1b/blob/main/main/command.c)）。其他
固件实现也鼓励遵循同样的约定以保持一致性，但这不是强制要求。

### 附录：本版本中移除的能力

为了配合上面提到的范围调整，这份协议早期版本中存在的下列能力，已经被完全移除，不再属于本项目的
范围：
- 设备身份认证（HMAC 签名、DeviceSecret 推导公式）——面向可信的内部网络环境，这一块被进一步
  简化到了明文 pid+sn 设备识别，完全没有签名/密钥校验。
- 会话 token 及其续期。
- 原来那个大得多的、服务器向设备推送控制指令的通道，包括配置轮询（原来的 `/device/poll`）、
  自定义探头读取配置（原来的 `set_probe`），以及固件 OTA 升级。**§9 后来重新引入了一个刻意做得
  很窄的 `cmd` 字段**（只有 reboot / 修改上报间隔，随 report 响应捎带，没有应答）——原来那个
  通道剩下的部分依然不在范围内。
- 自助式设备激活审批/密钥绑定流程（包括加密提交和 RSA 密钥对）。
